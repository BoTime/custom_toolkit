# Autopilot learnings

Distilled from the findings corpus across autopilot runs. Future runs' plan stages read this before planning. Kept bounded: rules are merged and rewritten rather than appended, and the run log keeps only the most recent runs.

Corpus shape so far, across 11 runs: 53 `plan` findings, 11 `spec`, 4 `implementation`, 2 `brief`. Almost everything that goes wrong is decided at plan time and transcribed faithfully downstream, so these rules are written for the plan stage.

## Planning rules

- **The plan is one document: it must agree with itself, and with the spec.** This is the largest family in the corpus and it produced the only critical to date. In `verify-screenshots-to-issue` the plan supplied both the `uploadSkipped` line that reports an unconfigured repo *and* the SKILL.md paragraph asserting such a repo appends nothing — a direct AC21 violation, shipped because each half looked right on its own. The same plan derived the object key's repo segment from the worktree where spec AC10 and its worked example key say the repository. Earlier runs: a `mergeConfig` snippet defaulting with `??` contradicted the plan's own "defaulting is never the fallback" constraint two sections above it; a findings paragraph advertised `stage_at_fault: "spec"` while the same plan's code hardcoded `"implementation"` for every unmet criterion. Rule: before shipping, read the prose against the code, the code against the spec's acceptance criteria, and treat the spec's worked examples as normative — a literal in an example is a requirement, not an illustration.

- **Before adding prose to a file a test measures, name the test and budget the addition.** Twice now a plan added SKILL.md prose without naming the pre-existing test that reads the file, and the run only learned at review. `autopilot-tiered-ceremony` tripped the `skill-sections` orphan-fragment test; `scaffold-autopilot-config` added 1,024 chars to a SKILL.md sitting 388 chars under the 42k ceiling in `skill-sections.test.mjs`, and the fix was the remedy that test's own comment prescribes — extract rationale to `references/rationale.md`. That extraction left 283 chars of headroom, so **the next SKILL.md prose addition needs its own extraction task in the plan**, not a hope. For every file a task edits, list the tests that read it as a document (size budgets, section contracts, orphan checks) alongside the tests that exercise its behaviour, and state the post-change number where a budget applies.

- **A dispatched agent's report is a claim; the artifact it was told to write is the evidence.** The `issue-25` run's `sdd` stage described three ledgered rulings and a final review finding 1 Important and 2 Minor issues, yet wrote no `findings.jsonl` at all, and nothing noticed until the next stage went looking. Softer versions recur: a TDD report quoting RED-phase counts the reviewer could not reproduce, a smoke-test report paraphrasing porcelain status output instead of quoting it, and in `scaffold-autopilot-config` a plan document left untracked while every earlier plan and the branch's own spec were committed. When one stage's output another stage consumes, name the artifact and its path, have the consuming side (or the orchestrator between them) check it exists and is well-formed before trusting the report, and say what happens when it is missing: park, ledger the gap, or degrade explicitly. Plan and spec documents are artifacts too: commit them.

- **Check every literal against the artifact it actually names, as that artifact is written, line breaks included.** Whatever the plan hands down verbatim ships unchanged: fixture indices, quoted substrings, regexes, identifiers, verification commands. `autopilot-tiered-ceremony` failed this three times in one plan — contract tests asserting `toContain('the round-5 breaker still applies')`, `/cannot be reviewed as one diff is two tasks/`, and `'more than 5 tasks'` against prose the same plan wraps across a newline, so all three were dead on arrival. Other misses: a fixture cited at index 7 that lives at 6; an unscoped one-liner check matching 4 entries instead of 2; a regex naming `implement_complex`, a depth-2 model-mapping name that is never a depth-1 agent name. If an assertion matches prose, match it the way the prose is laid out, or normalise whitespace first.

- **Read plan-supplied code blocks as production code before they ship, and route them through the module's own helpers.** They are transcribed verbatim, and every defect in them lands as a plan-stage finding. `scaffold-autopilot-config`'s inline `scaffoldConfig` body called `JSON.parse(readFile(defaultsPath))` when the module already had `readJson(path, readFile)`, so a corrupt defaults file would have surfaced as a bare `SyntaxError` with no path; before writing a code block, grep the target module for the helper that already does the job. Then check: shape guards on anything parsed (a manifest parsed with no non-object check let a `null` or scalar throw into the outer catch and exit non-zero); operation order against runtime dependencies (a `seed_command` specified before the dev server started seeded a database whose container was not up, parking a healthy branch); values that must vary per invocation (a hardcoded `{ round: 1 }` made a fix-round re-run write a duplicate findings line); process-global paths (a fixed temp path with no per-run scoping, clobber-prone and never cleaned); destructured defaults (a `deps` object destructured without per-key defaults throws `TypeError` on any partial caller); exit-code propagation (a CI step capturing stdout through command substitution always succeeded, so a broken script would leave CI green forever; helpers using `stdout` without checking `.code`); check-then-write gaps behind a "never overwrites" claim (open with `{ flag: 'wx' }` or say the claim is best-effort); argv and regex edge cases; and output polish such as unconditional plurals. And never route untrusted text through shell string interpolation — prose that embedded a GitHub issue title in a double-quoted `printf` was a live command-injection path; mandate `spawnSync` with array args instead.

- **Every file the change touches must be listed in the plan's File Structure — user-facing docs included — and every file edited gets a sweep for prose the change falsifies.** That list is the only inventory tasks act on; a file absent from it simply never gets edited. `verify-screenshots-to-issue` never listed `README.md`, so the new artifacts config block shipped documented nowhere outside the module and its test. The same blindness applies *within* a file: for every file a task edits, assign that task the sweep for guard sentences, inventories, frontmatter, and comments elsewhere in the file that the change falsifies. That was the whole of `issue-34` — a new report section inserted after a pre-existing "if the corpus is empty, say so and stop" sentence nobody rescoped, a run-directory inventory never updated for the `questions.jsonl` the same plan adds beside it, and a frontmatter `description` still describing one report after the command grew a second. `scaffold-autopilot-config` repeated it in README: "first run writes the full defaults" four lines above "most projects need only one key".

- **A hazard the plan names in prose but pins with no test is not handled.** `verify-screenshots-to-issue`'s plan named the verify-prefix ledger hazard in its own words and then specified no `nextStage` coupling test for the screenshot upload skip line. Naming a risk is not mitigating it: every hazard the plan states in prose must terminate in a named test, in a named guard, or in an explicit decision to accept it.

- **Trace every outcome the spec promises back to the data that must carry it, and match the prose's strength to what the code enforces.** The spec for `verify-screenshots-to-issue` claimed the round embedded in the object key would make the issue thread show before and after as two comments — but the manifest carries no round and the poster runs once, so the promised behaviour had no mechanism. `issue-34`'s spec justified capture-before-design-approved as preventing re-capture, when the real failure runs the other way (a crash between capture and the ledger entry resumes to phase 1 and re-captures), and the actual guard — skip if the corpus file already exists — was missing entirely. `scaffold-autopilot-config`'s spec said `test_command` "must be filled in before rerunning" when a rerun only warns and `land` parks later. Whenever a rationale rests on ordering or on a value's presence, walk the crash-and-resume path and name the field that carries it; whenever prose says "must" or "never", name the line that enforces it or soften the word.

- **Enumerate the invocation paths a new branch of behaviour covers.** `scaffold-autopilot-config`'s spec described the scaffold-and-stop path for a "plain" run, leaving `/autopilot resume` — which hits the same preflight — readable as excluded. When a change adds a gate at a shared entry point, list every command and mode that passes through it and say for each whether the gate applies.

- **A cited precedent transfers authority, not correctness. Check that it applies.** "Validate this the way `browser.ready_timeout_ms` is validated" was followed faithfully and was wrong: `browser` is a numeric perf knob where a default is harmless, whereas the new key gated an opt-in feature, so a non-object value passed validation and silently disabled exactly what the user asked for. Name which property makes the precedent transfer and compare failure modes on both sides; if the consequence of the lenient path differs, specify the behaviour directly.

- **Plan-authored tests: pin behaviour, and confirm every assertion can fail.** Do not pin an unverified literal — a plan test asserting a mandated string freezes it, and when review later finds the string wrong, plan governs and the run cannot fix it; that is how the dead `implement_complex` alternation shipped. Equally, an assertion that passes trivially hides the gap it was meant to close: a test named "works with a bare branch name" asserted a fast-forward of a branch onto itself as correct, and a workflow contract test never asserted the job actually pushes. Mutation-test load-bearing assertions by deleting the line they guard and watching them fail. And do not mandate imports nothing calls.

- **Prose a dispatched agent must execute is a contract; write it to one reading, and give every check its command.** Never use a word that names both a scope and a real structural unit of the same document ("include nothing from this subsection" collided with an actual `#### Derive the verify recipe`). For a gated or default-off path, state positively what is retained rather than relying on a negative exclusion. Use one term per concept (`separate subsystems` vs `unrelated subsystems` for the same boundary sent readers hunting for a distinction that did not exist), avoid appositives where two conditions are meant, keep numeral style consistent, and cover the failure branch — one setup paragraph told the agent to report `updated` or `skipped` but never that a non-zero exit means park the run. A preflight check with no command is a check an agent may skip or misjudge: `scaffold-autopilot-config` shipped "first check whether `<config>` exists" bare while every neighbouring check quoted its command, and an agent that skipped it would abort a valid run. New load-bearing SKILL.md prose needs a contract-test assertion; the repo already does this in `autopilot-sdd-contract`, `autopilot-findings-contract`, and `autopilot-ledger-coupling`.

- **Name the seams no single task's diff exposes — per-task review cannot see them.** `verify-screenshots-to-issue` is the clearest case yet: all four tasks passed task review clean, and every real defect, the critical included, surfaced only at whole-branch review. Same shape as the shell-injection path, and as the merge step that resolved per-key config while a later task's prose needed those resolved names but the CLI printed only `ok`. When one task produces a value another consumes, name the exact value crossing the boundary and pin it.

- **Scale task count to complexity, 1-5, and specify no more than the change needs.** Do not pad a small change into extra tasks, and do not compress unrelated work into one. Twice now the plan has specified knobs no caller varies — `putObject`'s `contentType` and the sigv4 query flag were single-caller parameters, implemented faithfully because the plan asked for them. If nothing overrides it, do not parameterise it.

- **If a plan mandates mirroring an existing module, say so and say what is being copied.** `issue-34` deliberately mirrored `autopilot-findings.mjs` in `autopilot-questions.mjs`, pre-existing plural wart included, which is defensible, but review had to rediscover the intent twice. Label deliberate duplication and name the trigger for factoring it out.

## Recent runs

- **scaffold-autopilot-config** — scaffold the project config from plugin defaults at preflight and stop for the user to fill in `test_command`. 1 task, 1 fix round. 10 findings: 5 plan (2 major, 3 minor), 3 spec minor, 2 brief minor, 1 implementation minor (accepted). The plan majors: Step 7 tripped the SKILL.md 42k size budget the plan never named (ruled: extract rationale to `references/rationale.md`, leaving 283 chars of headroom), and the reference `scaffoldConfig` body bypassed the module's `readJson` helper (fixed in `7854fc8`). The uncommitted plan doc was committed in the fix round; the six deferred minors are the check-then-write gap behind "never overwrites", three overstated or undecided prose claims (`test_command` gate, the `resume` path, README defaults contradiction), and the bare preflight check.
- **verify-screenshots-to-issue** — upload verify screenshots to object storage and post them to the issue. 4 tasks, all clean at task review; every defect surfaced only at whole-branch review. 7 findings: 6 plan (1 critical, 3 major, 2 minor) and 1 spec major. The critical was the plan contradicting itself across prose and code on the unconfigured-repo path (AC21). The plan majors: `README.md` missing from File Structure, a named ledger hazard left with no coupling test, and an object key repo segment derived from the worktree against spec AC10's example. The spec major promised a two-comment issue thread the manifest's data cannot produce.
- **issue-34-autopilot-log-brainstorm-clarifying-ques** — capture brainstorm clarifying questions into a per-run corpus, plus a second `autopilot-findings` report. 3 tasks, all clean at task review, 1 final-review fix round. 8 findings: 1 plan major (the unrescoped "stop if the corpus is empty" guard sentence, fixed in `40b6cf6`), 6 plan minors parked, 1 spec minor (inverted ordering rationale plus missing idempotency guard).
- **autopilot-tiered-ceremony** — tiered ceremony budgets for dispatch. 6 findings, all plan, 5 major. Three contract-test literals could not match the line-wrapped prose the same plan authored; a `??` default contradicted the plan's own constraint; an existing `skill-sections` orphan-fragment test the plan never named went red.
- **issue-25-autopilot-make-stage-dispatch-mechanical** — 3 tasks, 0 parked, 0 fix rounds, `verify` skipped. **No findings file:** `sdd` honoured none of the capture contract despite reporting three ledgered rulings and a final review with 1 Important and 2 Minor issues. The capture gap is the run's only durable signal; the substantive findings are lost.
