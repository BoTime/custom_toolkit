# Autopilot learnings

Distilled from the findings corpus across autopilot runs. Future runs' plan stages read this before planning. Kept bounded: rules are merged and rewritten rather than appended, and the run log keeps only the most recent runs.

Corpus shape so far: 43 `plan` findings, 7 `spec`, 3 `implementation`. Almost everything that goes wrong is decided at plan time and transcribed faithfully downstream, so these rules are written for the plan stage.

## Planning rules

- **A dispatched agent's report is a claim; the artifact it was told to write is the evidence.** A stage handed a written contract can simply not execute it and still return a confident report. The `issue-25` run's `sdd` stage described three ledgered rulings and a final review finding 1 Important and 2 Minor issues, yet wrote no `findings.jsonl` at all, and nothing noticed until the next stage went looking. Softer versions recur: a TDD report quoting RED-phase counts the reviewer could not reproduce, a smoke-test report paraphrasing `git status --porcelain` instead of quoting it. Rule: when one stage's output another stage consumes, name the artifact and its path, have the consuming side (or the orchestrator between them) check the file exists and is well-formed before trusting the report, and say what happens when it is missing: park, ledger the gap, or degrade explicitly.

- **Check every literal against the artifact it actually names, as that artifact is written, line breaks included.** Whatever the plan hands down verbatim ships unchanged: fixture indices, quoted substrings, regexes, identifiers, verification commands. The `autopilot-tiered-ceremony` run failed this three times in one plan: contract tests asserting `toContain('the round-5 breaker still applies')`, `/cannot be reviewed as one diff is two tasks/`, and `'more than 5 tasks'` against prose fragments the same plan wraps across a newline, so all three assertions were dead on arrival. Other misses: a fixture cited at index 7 that lives at 6; an unscoped `node -e` check matching 4 entries instead of 2; a regex naming `implement_complex`, an SDD depth-2 model-mapping name that is never a depth-1 agent name; two places in one brief quoting the same command line differently. If an assertion matches prose, match it the way the prose is laid out, or normalise whitespace before matching.

- **A plan's own code must obey the plan's own invariants, and the plan must name the tests it breaks.** Same run: a `mergeConfig` snippet defaulted with nullish-coalescing, so an explicit `{"tiers": null}` in a project config silently resolved to the shipped defaults with `ok:true`, directly contradicting the plan's stated "defaulting is never the fallback" constraint two sections earlier. And a new set of dispatch fragments tripped an existing `skill-sections` test asserting every fragment on disk is declared by a `STAGES` row; the plan named neither the file nor the test, so `npm test` simply went red. Before shipping, re-read prescribed snippets against the stated invariants, and grep for existing tests that enumerate the thing you are adding to.

- **When a plan adds to an existing document, it must also own the surrounding prose that still describes the old shape.** This was the dominant pattern in `issue-34`: three findings, one shape. A new report section was inserted right after a pre-existing "if the corpus is empty, say so and stop" sentence that was never rescoped, so an agent following the command literally halts before ever reaching the new section; a run-directory inventory list was never updated to mention the new `questions.jsonl` the same plan places beside those files; a skill's frontmatter `description` still described one report after the command grew a second. Rule: for every file a task edits, assign that task the sweep for guard sentences, inventories, frontmatter, and comments elsewhere in the same file that the change falsifies. A doc edit nobody owns simply never happens.

- **A cited precedent transfers authority, not correctness. Check that it applies.** "Validate this the way `browser.ready_timeout_ms` is validated" was followed faithfully and was wrong: `browser` is a numeric perf knob where falling back to a default is harmless, whereas the new key gated an opt-in feature, so a non-object value passed validation and silently disabled exactly what the user asked for. Name which property makes the precedent transfer and compare failure modes on both sides; if the consequence of the lenient path differs, specify the behaviour directly.

- **State the failure mode an ordering prevents, then check the ordering actually prevents it.** `issue-34`'s spec justified capture-before-design-approved as preventing re-capture; the real failure runs the other way, since a crash between capture and the ledger entry resumes to phase 1 and re-captures the same batch. The chosen order was right, the stated reason inverted, and the actual guard (skip if the corpus file already exists) missing entirely. Whenever a rationale rests on ordering, walk the crash-and-resume path explicitly and say whether an idempotency guard is needed.

- **Plan-authored tests: pin behaviour, and confirm every assertion can fail.** Do not pin an unverified literal. A plan test asserting a mandated string freezes it, and when review later finds the string wrong, plan governs and the run cannot fix it; that is how the dead `implement_complex` alternation shipped. Equally, an assertion that passes trivially hides the gap it was meant to close: a test named "works with a bare branch name" asserted a fast-forward of a branch onto itself as correct, and a workflow contract test never asserted the job actually pushes. Mutation-test load-bearing assertions by deleting the line they guard and watching them fail. And do not mandate imports nothing calls.

- **Read plan-supplied code blocks as production code before they ship.** They are transcribed verbatim, and every defect in them lands as a plan-stage finding. Check operation order against runtime dependencies (a `seed_command` specified before the dev server started seeded a database whose container was not up, parking a healthy branch); values that must vary per invocation (a hardcoded `{ round: 1 }` made a fix-round re-run write a duplicate findings line); process-global paths (a fixed `/tmp/autopilot-questions.json` with no `mktemp` or run-scoping, clobber-prone and never cleaned); destructured defaults (a `deps` object destructured without per-key defaults throws `TypeError` on any partial caller); exit-code propagation (a CI step that captured a script's stdout through command substitution always succeeded, so a broken script would leave CI green forever, and git helpers used `stdout` without ever checking `.code`); argv and regex edge cases; and output polish such as unconditional plurals.

- **Never route untrusted text through shell string interpolation.** Plan-specified prose that embedded a GitHub issue title in a double-quoted `printf` was a live command-injection path, and per-task review could not see it; it surfaced only at whole-branch review. Mandate `spawnSync` with array args, or have the script write the value itself via an injected file write.

- **Prose a dispatched agent must execute is a contract; write it to one reading.** Never use a word that names both a scope and a real structural unit of the same document: "include nothing from this subsection" collided with an actual `#### Derive the verify recipe` subsection. For a gated or default-off path, state positively what is retained instead of relying on a negative exclusion. Use one term per concept (`separate subsystems` vs `unrelated subsystems` for the same boundary sent readers hunting for a distinction that did not exist), avoid appositives where two conditions are meant ("confined to one module, satisfying one acceptance criterion" reads as a gloss), and keep numeral style consistent.

- **Guard load-bearing prose, and never document what the code cannot do.** New SKILL.md prose an agent must follow needs a contract-test assertion; the repo already does this in `autopilot-sdd-contract`, `autopilot-findings-contract`, and `autopilot-ledger-coupling`. In the other direction, do not document a case the same plan's code cannot produce: a findings paragraph advertised `stage_at_fault: "spec"` while the plan's own verify code hardcoded `"implementation"` for every unmet criterion. Make sure prose covers the failure branch too. One setup paragraph told the agent to report `updated` or `skipped` but never that a non-zero exit means park the run.

- **Name the seams no single task's diff exposes.** When one task produces a value another consumes, name the exact value crossing the boundary and pin it: a merge step resolved per-key config while a later task's prose needed those resolved names, but the CLI printed only `ok`.

- **If a plan mandates mirroring an existing module, say so in the plan and say what is being copied.** `issue-34` deliberately mirrored `autopilot-findings.mjs` in `autopilot-questions.mjs`, pre-existing plural wart included, which is defensible, but review had to rediscover the intent twice. Label deliberate duplication and name the trigger for factoring it out (here, a third corpus type).

- **Scale task count to complexity, 1-5.** The old "target 3-5" is retired. Do not pad a small change into extra tasks, and do not compress unrelated work into one.
