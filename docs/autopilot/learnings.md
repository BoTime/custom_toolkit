# Autopilot learnings

Distilled from the findings corpus across autopilot runs. Future runs' plan stages read this before planning. Kept bounded: rules are merged and rewritten rather than appended, and the run log keeps only the most recent runs.

## Planning rules

- **A dispatched agent's report is a claim; the artifact it was told to write is the evidence.** A stage handed a written contract can simply not execute it and still return a confident report — the `issue-25` run's `sdd` stage described three ledgered rulings and a final review finding 1 Important and 2 Minor issues, yet wrote no `findings.jsonl` at all, and nothing noticed until the next stage went looking for the file. The corpus has softer versions of the same failure: a TDD report quoting RED-phase pass/fail counts the reviewer could not reproduce, and a smoke-test report paraphrasing `git status --porcelain` output instead of quoting it. Rule: when one stage's output another stage consumes, name the artifact and its path, have the consuming side (or the orchestrator between them) check the file exists and is well-formed before trusting the report, and say what happens when it is missing — park, ledger the gap, or degrade explicitly. Never let "the agent said it did it" stand in for the file.

- **Check every literal against the artifact it actually names.** Whatever the plan hands down verbatim — a fixture index, a quoted substring, a regex, an identifier, a verification command — ships unchanged, so verify it against the artifact as written rather than the one you have in mind. Recent misses: a fixture entry cited at index 7 that lives at 6; a `node -e` check that matched 4 entries instead of the claimed 2 because it was unscoped; a mandated regex naming `implement_complex`, which is an SDD depth-2 model-mapping name and never a depth-1 agent name, so the alternation was dead on arrival; a verbatim test string and verbatim SKILL.md prose in the same brief that quoted the same command line differently and could not both be right.

- **A cited precedent transfers authority, not correctness — check that it applies.** "Validate this the way `browser.ready_timeout_ms` is validated" was followed faithfully and was wrong: `browser` is a numeric perf knob where falling back to a default is harmless, whereas the new key gated an opt-in feature, so a non-object value passed validation and silently disabled exactly what the user asked for. When you name an existing pattern as precedent, say which property makes it transfer and compare the failure modes on both sides; if the consequence of the lenient path differs, specify the behaviour directly instead of pointing at the precedent.

- **Plan-authored tests: pin behaviour, and confirm every assertion can fail.** Do not pin an unverified literal — a plan test asserting a mandated string freezes it, and when review later finds the string wrong, plan governs and the run cannot fix it (that is precisely why the dead `implement_complex` alternation shipped). Equally, an assertion that passes trivially hides the gap it was meant to close: a test named "works with a bare branch name" asserted a fast-forward of a branch onto itself as correct, and a workflow contract test never asserted the job actually pushes, so deleting the push line would have stayed green. Mutation-test load-bearing assertions — delete the line they guard and watch them fail.

- **Read plan-supplied code blocks as production code before they ship.** They are transcribed verbatim, and every defect in them lands as a plan-stage finding. Check operation order against runtime dependencies (a `seed_command` specified before the dev server had started seeded a database whose container was not up, parking a healthy branch); check values that must vary per invocation (a hardcoded `{ round: 1 }` made a fix-round re-run write a duplicate findings line); check that exit codes propagate (`echo version=$(node script.mjs) >> $GITHUB_OUTPUT` always succeeds, so a broken script would leave CI green forever; git calls used `stdout` without ever checking `.code`); check argv and regex edge cases.

- **Never route untrusted text through shell string interpolation.** Plan-specified prose that embedded a GitHub issue title in a double-quoted `printf` was a live command-injection path, and per-task review could not see it — it surfaced only at whole-branch review. Mandate `spawnSync` with array args, or have the script write the value itself via an injected file write.

- **Prose a dispatched agent must execute is a contract; write it to one reading.** Never use a word that names both a scope and a real structural unit of the same document — "include nothing from this subsection" collided with an actual `#### Derive the verify recipe` subsection, and an orchestrator could have read it as dropping the task-count budget and the learnings instruction for every default-mode run. For a gated or default-off path, state positively what is retained instead of relying on a negative exclusion. Use one term per concept (`separate subsystems` vs `unrelated subsystems` for the same boundary sent readers hunting for a distinction that did not exist), avoid appositives where two conditions are meant ("confined to one module, satisfying one acceptance criterion" reads as a gloss), and keep numeral style consistent.

- **Guard load-bearing prose, and never document what the code cannot do.** New SKILL.md prose that an agent must follow needs a contract-test assertion — the repo already does this in `autopilot-sdd-contract`, `autopilot-findings-contract`, `autopilot-ledger-coupling`. In the other direction, do not document a case the same plan's code cannot produce: a findings paragraph advertised `stage_at_fault: "spec"` while the plan's own verify code hardcoded `"implementation"` for every unmet criterion. When a plan changes a semantic or an error path, give some task the sweep for prose and comments elsewhere that still describe the old one, and make sure the prose covers the failure branch (a setup paragraph told the agent to report `updated` or `skipped` but never that a non-zero exit means park the run).

- **Name the seams no single task's diff exposes.** When one task produces a value another consumes, name the exact value crossing the boundary and pin it: a merge step resolved per-key config while a later task's prose needed those resolved names, but the CLI printed only `ok`. The same applies to documentation seams — if the change's payoff depends on another section knowing about it, assign that edit to a task, or it simply never happens.

- **Scale task count to complexity, 1–5.** The old "target 3–5" is retired. Don't pad a small change into extra tasks, and don't compress unrelated work into one.

## Recent runs

- **issue-25-autopilot-make-stage-dispatch-mechanical** — made stage dispatch mechanical so the orchestrator stops composing prompts inline. 3 tasks, 0 parked, 0 fix rounds; `verify` skipped (8 acceptance criteria, all non-UI). **No findings file:** `sdd` was given the findings capture contract and honoured none of it — no clean line per passing task, no line per finding — despite reporting three ledgered rulings and a final review with 1 Important and 2 Minor issues, all fixed. The capture gap is the run's only durable signal and is now the first planning rule; the substantive findings are lost.
- **ponytail-minimalism-contract** — opt-in, default-off `minimalism` mode injecting a YAGNI ladder into two dispatch prompts. 3 tasks, 0 parked, 0 task-level fix rounds, 1 final-review wave, 498 tests green. 3 confirmed findings: plan 1 major (the ambiguous "subsection" scope word above), spec 2 (the `browser.ready_timeout_ms` precedent that did not transfer; the dead `implement_complex` alternation, left unfixed because spec and plan mandate the string verbatim and a plan-authored test pins it).
- **plan-task-count-scale-to-complexity** — spec 4 (all minor, all PARKED, same shape: ambiguity in prose rules the plan stage must execute — appositive comma, near-synonym boundary terms, unclear referent, mixed numeral style), 1 task, 0 fix rounds. Changed the plan budget from "3–5" to "1–5, scaled to complexity".
