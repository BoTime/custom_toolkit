# Autopilot learnings

Distilled from the findings corpus across autopilot runs. Future runs' plan stages read this before planning. Kept bounded: rules are merged and rewritten rather than appended, and the run log keeps only the most recent runs.

Corpus shape so far, across 14 runs: 80 findings — 59 at `plan`, 12 at `spec`, 7 at `implementation`, 2 at `brief`; 1 critical, 25 major, 4 important, 50 minor. Almost everything that goes wrong is decided at plan time and transcribed faithfully downstream, so these rules are written for the plan stage. The most recent run is the corpus's first with zero findings — three tasks, no fix rounds, every task clean at review — which is what these rules are for.

## Planning rules

- **The plan is one document: it must agree with itself, and with the spec.** This is the largest family in the corpus and it produced the only critical to date. In `verify-screenshots-to-issue` the plan supplied both the `uploadSkipped` line that reports an unconfigured repo *and* the SKILL.md paragraph asserting such a repo appends nothing — a direct AC21 violation, shipped because each half looked right on its own. Earlier runs: a `mergeConfig` snippet defaulting with `??` contradicted the plan's own "defaulting is never the fallback" constraint two sections above it; a findings paragraph advertised `stage_at_fault: "spec"` while the same plan's code hardcoded `"implementation"`. Rule: before shipping, read the prose against the code, the code against the spec's acceptance criteria, and treat the spec's worked examples as normative — a literal in an example is a requirement, not an illustration.

- **Verify every repository-state claim against the repo, and order tasks so each one's preconditions hold at its own position.** `autopilot-superpowers-path-layout` asserted in Task 2 that the worktree had no `.claude/autopilot.json`; the file was tracked and present, so the path resolver would have returned the legacy path and the task's own new tests would have failed. The plan was only rescued because the implementation swapped in Task 3 — the task that `git mv`-s the config — ahead of it. A relocation plan is especially exposed: a task that tests the *new* layout cannot run while the *old* artifact is still on disk. For every "the repo currently has / does not have X" sentence, run the command that checks it and quote the result; for every task, state the artifacts that must already have moved, been deleted, or been created before it starts. If the ordering that satisfies those preconditions is not the written order, the written order is the defect.

- **A global ruling and a task's literal step text are both governing; when they disagree, the ruling is usually the one that is wrong.** `small-tier-scratch-docs` hit this twice in one run: the plan ruled that `plan-body.md` and `spec-body.md` line 1 relocate *byte-identically* into their new homes, while the same plan's Step 3 literal file content reworded both, because those bodies are now shared with a new tier where the old wording would be actively misleading. Both deviations were confirmed and accepted as implemented; the ruling, written before the sharing was worked through, was the defect. When a plan mandates verbatim relocation of text into a file more than one caller will render, check the text is neutral across every caller first — and if it is not, drop the identity ruling instead of leaving two governing statements in conflict.

- **Before adding or moving prose in a file a test measures, name the test and budget the change.** Three runs now. `autopilot-tiered-ceremony` tripped the `skill-sections` orphan-fragment test; `scaffold-autopilot-config` added 1,024 chars to a SKILL.md sitting 388 chars under the 42k ceiling. The remedy both times — extract rationale to `references/rationale.md` — has its own failure mode, seen in `small-tier-scratch-docs`: moving the run-directory reasons out of SKILL.md left `autopilot-findings-contract.test.mjs` asserting against SKILL.md, where its two reason tests then passed only on coincidental unrelated text, plus a stale header comment claiming those rules live there. The extraction was right; the un-rescoped test was the defect. For every file a task edits, list the tests that read it *as a document* (size budgets, section contracts, orphan checks) alongside the tests that exercise its behaviour, state the post-change number where a budget applies, and when text moves between files, move the assertions with it.

- **Every file the change touches must be listed in the plan's File Structure — user-facing docs and in-code prose included — and every file edited gets a sweep for prose the change falsifies.** That list is the only inventory tasks act on; a file absent from it never gets edited. `verify-screenshots-to-issue` never listed `README.md`, so a new config block shipped documented nowhere. The same blindness applies *within* a file: assign each task the sweep for guard sentences, inventories, frontmatter, JSDoc, and comments elsewhere in the file that the change falsifies, and make some task's file list own each one. That was the whole of `issue-34`; `scaffold-autopilot-config` repeated it in README ("first run writes the full defaults" four lines above "most projects need only one key"); `small-tier-scratch-docs` shipped a shared body line rendering `Worktree (work only here)` above small-tier fragments that instruct writing outside the worktree; `autopilot-superpowers-path-layout` left `autopilot-config.mjs`'s own `loadConfig` JSDoc naming the old `.claude/autopilot.json` path the same branch had just falsified. When a change renames or relocates a path, grep the old string across the whole repo and assign every hit — comments included — to a task.

- **A dispatched agent's report is a claim; the artifact it was told to write is the evidence.** The `issue-25` run's `sdd` stage described three ledgered rulings and a final review with 1 Important and 2 Minor issues, yet wrote no `findings.jsonl` at all, and nothing noticed until the next stage went looking. Softer versions recur: a TDD report quoting RED-phase counts the reviewer could not reproduce, a smoke-test report paraphrasing porcelain status output instead of quoting it, a plan document left untracked while every earlier plan was committed. When one stage's output another stage consumes, name the artifact and its path, have the consuming side check it exists and is well-formed before trusting the report, and say what happens when it is missing. Plan and spec documents are artifacts too: commit them.

- **Check every literal against the artifact it actually names, as that artifact is written, line breaks included.** Whatever the plan hands down verbatim ships unchanged: fixture indices, quoted substrings, regexes, identifiers, verification commands. `autopilot-tiered-ceremony` failed this three times in one plan — contract tests asserting three prose literals the same plan wraps across a newline, so all three were dead on arrival. Other misses: a fixture cited at index 7 that lives at 6; a regex naming `implement_complex`, a depth-2 model-mapping name that is never a depth-1 agent name; an illustrative `node -e` verification snippet whose match was unscoped and returned 4 hits where the plan claimed 2. If an assertion matches prose, match it the way the prose is laid out, or normalise whitespace first — and run any verification command you quote.

- **Read plan-supplied code blocks as production code before they ship, and route them through the module's own helpers.** They are transcribed verbatim, and every defect in them lands as a plan-stage finding. `scaffold-autopilot-config`'s inline `scaffoldConfig` parsed the defaults file directly when the module already had a `readJson` helper, so a corrupt file surfaced as a bare `SyntaxError` with no path. Then check: shape guards on anything parsed; input leniency against the spec's stated format (a `parseVersion` regex accepting `01.2.3`); operation order against runtime dependencies (a `seed_command` before the dev server started parked a healthy branch); values that must vary per invocation (a hardcoded round 1 made a fix round write a duplicate findings line); subprocess exit codes before using stdout; process-global paths and `process.argv[1]` guards; destructured defaults; exit-code propagation (a CI step capturing stdout always succeeded); check-then-write gaps behind a "never overwrites" claim; dead code a deletion step leaves behind; and output polish such as unconditional plurals. Never route untrusted text through shell string interpolation — prose embedding a GitHub issue title in a double-quoted `printf` was a live command-injection path; mandate array-args spawning instead.

- **A hazard the plan names in prose but pins with no test is not handled.** `verify-screenshots-to-issue`'s plan named the verify-prefix ledger hazard in its own words and then specified no `nextStage` coupling test for the screenshot upload skip line. Every hazard the plan states in prose must terminate in a named test, in a named guard, or in an explicit decision to accept it.

- **Trace every outcome the spec promises back to the data that must carry it, name every invocation path a new branch covers, and match the prose's strength to what the code enforces.** `verify-screenshots-to-issue`'s spec claimed the round embedded in the object key would make the issue thread show before and after as two comments — but the manifest carries no round and the poster runs once. `issue-34`'s spec justified capture-before-design-approved as preventing re-capture when the real failure runs the other way, and the actual guard was missing entirely. `scaffold-autopilot-config` did both halves: its spec said `test_command` "must be filled in before rerunning" when a rerun only warns, and it described the scaffold-and-stop path for a "plain" run, leaving `/autopilot resume` — which hits the same preflight — readable as excluded. Whenever a rationale rests on ordering or on a value's presence, walk the crash-and-resume path and name the field that carries it; when a change adds a gate at a shared entry point, list every command, mode, and tier that passes through it; whenever prose says "must" or "never", name the line that enforces it or soften the word.

- **A cited precedent transfers authority, not correctness. Check that it applies.** "Validate this the way `browser.ready_timeout_ms` is validated" was followed faithfully and was wrong: `browser` is a numeric perf knob where a default is harmless, whereas the new key gated an opt-in feature, so a non-object value silently disabled exactly what the user asked for. Name which property makes the precedent transfer and compare failure modes on both sides.

- **Plan-authored tests: pin behaviour, and confirm every assertion can fail.** Do not pin an unverified literal — a plan test asserting a mandated string freezes it, and when review finds the string wrong, plan governs and the run cannot fix it; that is how the dead `implement_complex` alternation shipped. Equally, an assertion that passes trivially hides the gap it was meant to close. `small-tier-scratch-docs` mandated four document-shape gate tests of which two (fragment ordering, plan-path required on every tier) only exercised pre-existing generic compose machinery and could never have gone red for the change, while the real coverage sat elsewhere in a contract-test expectation; earlier runs shipped a "works with a bare branch name" test asserting a fast-forward of a branch onto itself, and a workflow contract test that never asserted the job pushes. For each test the plan mandates, name the line of *new* wiring it would fail without, mutation-test load-bearing assertions by deleting that line, and do not mandate imports nothing calls.

- **Prose a dispatched agent must execute is a contract; write it to one reading, and give every check its command.** Never use a word that names both a scope and a real structural unit of the same document ("include nothing from this subsection" collided with an actual heading of that name). For a gated or default-off path, state positively what is retained rather than relying on a negative exclusion. Use one term per concept, avoid appositives where two conditions are meant, and cover the failure branch — one setup paragraph told the agent to report `updated` or `skipped` but never that a non-zero exit means park the run. A preflight check with no command is a check an agent may skip: `scaffold-autopilot-config` shipped "first check whether the config exists" bare while every neighbouring check quoted its command. New load-bearing SKILL.md prose needs a contract-test assertion; the repo already does this in `autopilot-sdd-contract`, `autopilot-findings-contract`, and `autopilot-ledger-coupling`.

- **Name the seams no single task's diff exposes — per-task review cannot see them.** `verify-screenshots-to-issue` is the clearest case: all four tasks passed task review clean, and every real defect, the critical included, surfaced only at whole-branch review. `small-tier-scratch-docs` repeated the shape — its two accepted line-1 deviations and the cross-tier worktree contradiction were all whole-branch findings. When one task produces a value another consumes, name the exact value crossing the boundary and pin it.

- **Scale task count to complexity, 1-5; specify no more than the change needs, and label deliberate duplication.** Do not pad a small change into extra tasks, and do not compress unrelated work into one. Twice the plan has specified knobs no caller varies — an object-store content type and a signing query flag were single-caller parameters, implemented faithfully because the plan asked. If nothing overrides it, do not parameterise it. The mirror of this is over-extraction: `small-tier-scratch-docs` told a step to keep exactly one sentence and the implementation kept a fuller one, benign here, but say whether a stated extraction boundary is exact or a floor. And when a plan mandates mirroring an existing module — `issue-34` deliberately mirrored `autopilot-findings.mjs` in `autopilot-questions.mjs`, pre-existing plural wart included — say so and name the trigger for factoring it out, or review rediscovers the intent every round.

## Recent runs

- **issue-48-use-the-orca-as-the-worktree-provider** — make Orca the default worktree provider for the `setup` stage, with git as an explicit alternative and automatic fallback, and teach the reaper to remove Orca worktrees through `orca worktree rm`. Standard tier, 3 tasks, 0 parked, 0 fix rounds; verify skipped (no `(ui)` criteria). **0 findings — every task clean at review, the first such run in the corpus.** Three things the plan did that the rules above ask for: it treated the provider as an ergonomic upgrade that must never park a run, so every failure path had a named fallback; it made the ledger's `worktree:` line the single source of truth for path *and* branch once the branch name stopped being derivable from the run name; and it added a `autopilot-worktree-contract.test.mjs` alongside the new module rather than leaving the new SKILL.md prose unpinned.
- **autopilot-superpowers-path-layout** — relocate the project config to `.superpowers/autopilot/configs/` and run state to `.superpowers/autopilot/runs/<run>/`. Large tier, 4 tasks, 42 steps, 0 parked, no fix rounds; verify skipped (13 ACs, none `(ui)`). 2 findings, both plan: a major false precondition — Task 2 asserted the worktree had no `.claude/autopilot.json` when it was tracked and present, so the new default-config tests would have failed until Task 3's `git mv` ran first (resolved by executing 3 before 2) — and a minor missed falsification site, `autopilot-config.mjs`'s `loadConfig` JSDoc still naming the old path with no task's file list owning it. Operationally: opus hit a 429 monthly spend limit mid-`sdd` and task 4 ran on sonnet; the worktree reaper was blocked by the harness auto-mode classifier, leaving 6 stale worktrees.
- **small-tier-scratch-docs** — add a small ceremony tier with shared spec/plan body fragments and scratch-doc placement. 3 tasks, 1 fix round. 8 findings: 5 plan (3 major, 2 minor), 1 spec minor, 2 implementation minor. The plan majors are two instances of one class — a byte-identity relocation ruling contradicted by the plan's own reworded Step 3 text for both `plan-body.md` and `spec-body.md`, accepted as implemented because the shared bodies must read correctly on the small tier — plus a rationale extraction that left two `autopilot-findings-contract` assertions and a header comment pointing at SKILL.md, fixed by rescoping them to `references/rationale.md`.
- **scaffold-autopilot-config** — scaffold the project config from plugin defaults at preflight and stop for the user to fill in `test_command`. 1 task, 1 fix round. 10 findings: 5 plan (2 major, 3 minor), 3 spec minor, 2 brief minor. The plan majors: one step tripped the SKILL.md 42k size budget the plan never named (ruled: extract rationale, leaving 283 chars of headroom), and the reference scaffold body bypassed the module's own JSON-reading helper.
- **verify-screenshots-to-issue** — upload verify screenshots to object storage and post them to the issue. 4 tasks, all clean at task review; every defect surfaced only at whole-branch review. 7 findings: 6 plan (1 critical, 3 major, 2 minor) and 1 spec major. The critical was the plan contradicting itself across prose and code on the unconfigured-repo path (AC21); the spec major promised a two-comment issue thread the manifest's data cannot produce.
